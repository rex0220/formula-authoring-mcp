# 項目検証プラグインの設定（fv_* のツール）

kintone の**項目検証プラグイン（rex0220 field validation）Ver.72 以降**の設定 JSON を、要件から作る・直す・確かめる手順。
項目検証の式は計算式プラグインと同じ言語で、formula MCP は**計算式プラグインの zip（Ver.102 以降。試用版でよい）**のエンジンで評価する（項目検証の zip は要らない。`fml_status` で zip を確かめる）。
ツールは `fv_save_settings` / `fv_update_rows` / `fv_summary` / `fv_normalize` / `fv_check` / `fv_pull` / `fv_diff`。項目・レコード・作業フォルダーは計算式と同じ `fml_fields` / `fml_record` / `fml_files` / `fml_take` / `fml_edit`（`plugin: "field-validation"`）を使う。**`fml_save_settings` / `fml_update_fields` / `fml_calc` に項目検証の設定を渡さない**。

## 項目検証でできること（設定の列）

| 列 | 内容 |
| --- | --- |
| 必須条件・入力不可・非表示 | 式が真のとき、その項目を必須に・入力不可に・非表示にする |
| 初期化 | 隠れたまま保存するとき、その項目を初期値に戻す（初期値が空のルックアップは解除） |
| 検証条件 | 条件の式が真のとき、メッセージの式（日・英・中）でエラーにする。上から最初の 1 つ |
| テーブル内非表示 | テーブルの子の列を隠す（テーブルの行の `tblfields`） |
| 行の追加・削除の非表示 | テーブルの ＋ / × を隠す（行 `<テーブル>($ADD)` / `($DEL)` の非表示） |
| 要素 ID の行・グループ | スペース・ラベル・罫線（行 `(要素ID)`）とグループを隠す |
| 共通の設定 | 有効、非表示前処理、枠線（必須で未入力・必須で入力済み・エラーの色と太さ）、NOTE と説明 |

## 読むもの（fml_docs の章）

| 知りたいこと | 章 |
| --- | --- |
| 設定ファイルの形（封筒、キー、列ごとに置けない型、書かないキー、更新系の関数） | `fv-spec` |
| **やりたいこと（必須・入力不可・非表示・初期化・検証条件・テーブル・ステータス・日付・イベント）の書き方** | `fv-patterns`（P1〜P14。どれも確かめた例）。関数名から探す前にこちら |
| 雛形（封筒 + 元の値） | `fv-sample-settings` |
| 関数の引数と説明 | `function-list`（計算式と同じ。ただし更新系の関数は項目検証では使わない） |
| 接続のファイル、テスト用アプリとテストデータ、要件を AI が作る | `connections`、`test-app`、`requirements`（下の「計算式の手順の読み替え」） |

## 新しい設定を作る

1. **アプリ番号** — 要件に番号が無ければ利用者に聞く（Claude Code では kintone MCP の `kintone-get-apps` で探してよい。候補が複数あれば推測せず聞く）
2. **項目** — `fml_fields`（app、profile）。式には**ラベルでなくフィールドコード**を書く。スペース・ラベル・罫線を隠すなら要素 ID（要約の「項目検証の要素 ID の行」。fieldcode は `"(要素ID)"`）。○ と最後の行（ボタン・表示の行）は計算式のもので、項目検証では見ない。似たラベルは推測しない
3. **レコード** — 確かめに使う 1〜3 件（条件に合うもの・合わないもの、テーブルの行があるもの）を `fml_record`（app、id）で取る。返るのは形の要約だけ。**テスト用アプリのテストデータのレコードを使う**（`fv_check` の結果に、メッセージの式と初期化の値としてレコードの値が入りうる）
4. **仕様の確認（設計の前）** — 表にして利用者に確かめる: どのイベントで効かせるか（作成・編集・一覧の編集。既定はどれでも）、隠したときに値を消すか（初期化）、メッセージの文と英語・中国語、ステータスの名前、テーブルは行ごとか全体か、空・未選択のときの扱い、**フォームで必須の項目は必須条件を変えられない**こと
5. **設定 JSON を保存** — `fv-sample-settings` を写し、**封筒**で `fv_save_settings` に渡す（path はアプリのフォルダーの中の `FV-APP<番号>-<アプリ名>.json`。接続のファイルが無いときは `settings/FV-APP<番号>-<アプリ名>.json` と `fields`。計算式の設定 `APP<番号>-….json` と名前を分ける）。`pluginID` は `"rex0220 field validation plugin"`、`PluginVersion` は `"72"`、`appId` は番号。`pluginInfos` には設定を置く行だけを書き、`state: true`（「使う」）にする。式は `fv-spec` の「列ごとに置けない型」を守り、書き方は `fv-patterns` から選ぶ。下の「式の決まり」を守る。保存は検査を通る（エラーがあれば invalid で保存されない。下の表で直してもう一度）。**警告は消さずに利用者に伝える**。保存したファイルは既定値を補った形（フォームで必須の行も入る。レイアウトの順）
6. **fv_check** — `fv_check`（path、records、events）。例 events `["app.record.create.show", "app.record.create.submit"]`（編集なら `app.record.edit.…`、値の変更は `app.record.edit.change.<項目コード>`、一覧の編集は `app.record.index.edit.submit`）。項目ごとの 非表示 / 入力不可 / 必須 / 誤りの文 / 保存の前に入れる値 を見て、要件どおりか確かめる。英語・中国語のメッセージは `lang`。結果は模擬（kintone は変えない）で、レコードの画面とは、必須の未入力を常に文に出す・テーブルの子の隠れたルックアップも解除する・グループは出さない、が違う。画面への反映（枠線の色、グループの開閉）は実機で。直すときは `fv_summary`（digest）→ `fv_update_rows` → もう一度 `fv_check`
7. **反映方法を伝える** — アプリの設定 → プラグイン → 項目検証プラグインの設定 → **設定をアップロード** → 取り込み方を選ぶ（設定画面の言葉「全置換」「項目の置換」で書く。設定がまだ無いアプリは「全置換」、既存の設定の一部を変えるなら「項目の置換」で対象の項目をチェック。前の設定を取り込んだか分からなければ両方を書く）→ **保存する**（「運用環境に反映」をチェックするとアプリの更新まで行う）。**既存のレコードの値は変わらない**。ただし、次に既存のレコードを編集して保存するとき、新しい必須条件・検証条件で止まることがあり、隠れて「初期化」がオンの項目は初期値に戻る — このことを必ず添える。伝える文は 1 つにまとめ、止まりそうなレコードがあればそれを添える（同じことを 2 回書かない）

## 既存の設定を変える

1. **今の設定を取る** — `fv_pull`（app、profile）でアプリのフォルダーに `rex0220-field-validation-app<番号>-<日時>.json` で取る（API ラボの機能が有効なとき）。取れなければ、利用者に項目検証の設定画面の「設定をダウンロード」を頼み、`inbox/` に置いてもらって `fml_take`。`fml_files`（app）の `fvSnapshots` の先頭が今の設定
2. **写す** — `fml_edit`（app、`plugin: "field-validation"`）で `…-edit.json` に写す。**ダウンロード / pull のファイルは書き換えない**
3. **見る** — `fv_summary`（path = -edit.json）で全体と digest、`field` で直す行の式の全文
4. **直す** — `fv_update_rows`（path、expectedDigest、rows）。rows は直す行（`fieldcode` と、変えるキー `state` / `formulaSet` / `disabledSet` / `hideSet` / `init` / `condInfos` / `tblfields`）の配列。キーごとに丸ごと置き換える（`condInfos` は検証条件の全部、テーブルの行の `tblfields` は列の非表示の全部を書く）。設定に無い行も足せる（`state` を省けば true）。共通の設定（有効、非表示前処理、NOTE、説明、枠線）は `common`。保存は検査を通る（エラーがあれば invalid で変わらない）。結果の `diff` に変わった行
5. **確かめと差** — `fv_check` で判定を確かめ、`fv_diff`（before = ダウンロード / pull、after = -edit.json）を利用者に見せる
6. **反映方法** — 上の 7 と同じ。取り込み方は「項目の置換」で、変えた項目だけチェックしてもらう（共通の設定を変えていなければ「共通の設定」のチェックを外す）

接続のファイルが無いとき（`fml_workspace_status` の mode が not-configured）は、`fv_pull` / `fml_take` / `fml_edit` は使えない。利用者に設定画面のダウンロードを `settings/` に置いてもらい、そのファイルは直さず、写しを `fv_save_settings` で作る（path は `settings/FV-APP<番号>-<アプリ名>-直し.json` のように、ダウンロードの名前でも `-edit.json` でもない名前。content はダウンロードと同じ封筒（保存値のキーが入っていても読める）。fields は `fields/<番号>.json`）→ `fv_summary`（digest）→ `fv_update_rows` → `fv_check`（records は `records/<番号>-<レコード番号>.json`。利用者が置く）→ `fv_diff`。

## 設定の解説を頼まれたら

1. `fv_summary` で行の一覧、`field` で式の全文を見る（設定ファイルを Read で開かない）
2. 書き方の型は `fv-patterns` のパターン名で言う。関数は `function-list` で確かめる
3. 説明に入れること: どの項目が、どんな条件で、必須・入力不可・非表示になるか、どの検証条件でどの文が出るか、初期化で何が消えるか、イベントで変わる式（`EV_INFO`）、ユーザー・ステータスで変わる式、気づいた問題（日付を `TODAY()` と直接比べている、メッセージが `"…"` で囲まれていない、URL の文字列、「使う」がオフの行）
4. 必要なら `fml_record` → `fv_check` で、そのレコードに当てた判定を添える（模擬）
5. 分からない点は推測せず「確かめたいこと」として書く

## 計算式の手順の読み替え

`connections`・`test-app`・`requirements` の章は、次を読み替えてそのまま使う。

- `fml_pull` → `fv_pull`、`fml_save_settings` / `fml_update_fields` → `fv_save_settings` / `fv_update_rows`、`fml_calc` → `fv_check`、`fml_summary` / `fml_diff` → `fv_summary` / `fv_diff`、`fml_normalize` → `fv_normalize`
- アプリのフォルダーの項目検証のダウンロード / pull は `rex0220-field-validation-app<番号>-<日時>.json`（計算式と別に、一番新しいものが今の設定）。`fml_files`（app）は両方を出し（`snapshots` と `fvSnapshots`）、`fml_take` は両方を移す
- テスト用アプリ: 項目検証のプラグインが写っていなければ、アプリの設定 → プラグインで追加してもらう
- 式の断片の試し（`fml_try`）は計算式のサンプルアプリで動く。条件の式の結果（真か偽か）を確かめるだけなら使ってよい（更新系の関数は試さない）。項目検証の判定は `fv_check`

## 結果（fv_save_settings / fv_update_rows / fv_normalize の findings）

エラーが 1 つでもあると invalid（保存しない。`fv_check` もしない）。

| エラー | 意味と直し方 |
| --- | --- |
| `schema.json` / `schema.rows` / `schema.unknown-key` / `schema.type` | JSON として読めない、行の形が違う、知らないキー（書き間違い。設定画面は黙って捨てる）、型が違う（`state` / `init` は true / false、式は文字列） |
| `schema.duplicate` | 同じ項目の行が 2 つ（1 つにまとめる） |
| `envelope.plugin` / `envelope.version` / `envelope.app` | `pluginID` が `"rex0220 field validation plugin"` でない / `PluginVersion` が 72 未満（項目検証を 72 以降にしてダウンロードし直す）/ `appId` が fields のアプリと違う |
| `plugin.version` | 計算式プラグインの zip が Ver.102 未満（利用者に新しい zip（試用版でよい）を頼む） |
| `field.missing` | 今のアプリに無い行・テーブルの子（ラベルで書いた、綴り、消えた項目、要素 ID の違い） |
| `field.column` | その型には置けない列（`fv-spec` の「列ごとに置けない型」）。例: 計算・グループに必須条件、添付に初期化、グループに検証条件 |
| `formula.update` | 更新系の関数（FSET、FSET_TADD、BUTTON、DIALOG、CLIPBORD_WRITE、EV_SET、TLTABLE、TABLE_SORT、TABLE_MAP、TABLE_DATA、CSV_TVAL）。項目検証では使わない（「使う」がオフの行でも） |
| `formula.function` / `formula.syntax` / `formula.error` | 無い関数 / 括弧・文字列が閉じていない / エンジンが評価できない（無い項目 `FIELD CODE NOT FOUND`、引数の数など。エンジンの文を読む） |
| `cond.empty` | 「使う」がオンの検証条件で、条件かメッセージ（日）が空。テーブル内非表示で式が空 |
| `size.limit` | 保存値が大きすぎる |

| 警告（消さずに利用者に伝える） | 意味 |
| --- | --- |
| `formula.strip` | 文字列の中に `//` か改行がある（保存で消えて式が切れる。URL は書かない） |
| `message.form` | メッセージが項目の値だけ（文は `"…"` で囲む。意図どおりなら残す） |
| `formula.volatile` | `TODAY` / `NOW` / `RAND` など、評価のたびに変わる関数 |
| `required.form` | フォームで必須の項目に必須条件の式（設定画面が `"1"` に戻すので使われない） |
| `init.nohide` | 初期化がオンだが非表示の式が無い（隠れないので初期化されない） |
| `state.off` / `formula.off-error` | 「使う」がオフなので式が効かない / オフの行の式の誤り（オンにすると保存で止まる） |
| `border.value` | 枠線の幅・色が決まりに合わない（既定に戻る） |

情報（捨てるキー、エンジンの版の違い `engine.differs`、ログインユーザー・イベント・ユーザー情報で変わる関数、隠れる項目の必須、フォームで必須の行、保存値の大きさ、内部番号は設定画面が付ける）は要るときだけ伝える。`fv_check` の `contextLine` にも評価のエンジン（計算式の zip の版と、項目検証の同梱との同じ / 違う）が出る。

## 式の決まり（守らないと動かない・壊れる）

- **封筒なしの JSON は誤り**。`pluginID` / `PluginVersion` / `appId` を書く
- 式には**フィールドコード**を書く。条件は真（true・0 以外の数・空でない文字列）のとき効く。空の式は「設定なし」
- **メッセージも式**。文は `"…"` で囲み、項目の値は `&` でつなぐ（`"金額は " & 金額 & " 円"`）。英・中が空なら日本語が出る
- **日付の項目は式の中では数（秒）**、`TODAY()` は文字列（"YYYY-MM-DD"）。`申請日 > TODAY()` は比べられない。`DATE_DIFF("TODAY", 申請日, "days") > 0` のように日数で比べ、空の日付は `AND(申請日, …)` で除く（`fv-patterns` の P7）
- `//` から行末まではコメントで、保存のときに改行と一緒に消える。**文字列の中の `//` も消える**（`"https://…"` を書かない）
- **更新系の関数は使わない**（値を変える・テーブルを作る関数。式は表示・値の変更・保存の前・一覧の編集のたびに評価される）
- テーブルの子の式は同じ行の値を読む。テーブルの外から子を見るなら集計関数（`SUM(金額T)` など）
- 判定するのは「使う」がオンの行だけ（フォームの文字数・数値の範囲の文も、オンの行だけ）。順は 非表示 → 入力不可（隠れていれば判定しない）→ 必須（隠れても入力不可でもないとき）。文は 1 項目 1 つで、制約の文 → 検証条件 → 必須の未入力 の順
- フォームで必須の項目の必須条件は `"1"` に固定（変えられない）。ラジオボタンは kintone で常に必須
- グループを隠しても中の項目の判定は変わらない（画面で中の項目も見えなくなるだけ）
- 内部番号（`fieldno` / `ptno`）は設定画面が保存のときに付ける。保存したファイルには無い（正しい）
- ログインユーザー・ステータス・イベント（`EV_INFO`）で変わる式は、どの場合にどうなるかを表にして利用者に示す（`fv_check` の `user` / `events`）
- `fv_check` の結果には、メッセージの式の結果と初期化の値が出る（項目の値をつなぐメッセージなら、レコードの値が入る。1 つ 200 文字で切る）。確かめにはテストデータのレコードを使う
