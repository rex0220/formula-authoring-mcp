# 新しい設定を作る

要件は `requirements/` のファイル（利用者が書いたもの、または AI が書いて利用者が OK したもの。requirements の章）、またはチャットで受け取る。状態は `fml_status` / `fml_workspace_status` で確かめる（手順の文から推し量らない）。

1. **アプリ番号** — 要件に番号があればそれを使う。名前だけなら利用者に番号（か URL）を聞く（Claude Code では kintone MCP の `kintone-get-apps` に `name` と `limit` を付けて探してよい。**候補が複数あれば推測せず利用者に聞く**）
2. **項目** — `fml_fields`（app、profile）。アプリのフォルダー `kintone/<profile>/<番号>-<アプリ名>/` に `fields.json` ができ、1 項目 1 行の要約（レイアウトの順。○ = 計算式を設定できる型）が返る。計算式には**ラベルでなくフィールドコード**を書く。要件のラベルをどのコードに対応させたかを利用者に示す。似たラベルは**推測しない**。○ の無い型（CALC、ルックアップのコピー先など）には計算式を置けない
3. **レコード** — 代表の 1 件（テーブルが複数行、空の項目がある）を `fml_record`（app、id）で取る（Desktop は `kintone_list_records` で数件の形を見て選ぶ。Claude Code は kintone MCP の `kintone-get-records` で選んでよいが、値は会話に出さない）。返るのは形の要約だけ。設定を保存した後は `fieldsFrom` で使う項目だけに絞って取り直してよい
4. **仕様の確認（設計の前）** — 要件のあいまいな点と設計の選び方を、計算式を書く前に表にして利用者に確かめる。確かめること: 集計で該当の無い分類の行を出すか（固定の行で 0 を出す / 該当のある分類だけ）、行の順（分類の定義順 / 金額順 / 入力順）、空のときの値（空 / 0）、端数（四捨五入・切り捨て、桁）、既存の入力値を計算式で上書きしてよい項目か、ボタンで動かすか自動か、どのイベントで動くか。**テストのレコードに無いが起こりうる値**（選択肢の未選択、空の金額、同じ値の重複、該当なし、0 件）をどう扱うかも聞く。patterns の章に同じ目的の別のやり方があれば、それぞれの結果の違いを添えて選んでもらう。既存の入力値の上書き、端数、空と 0、対象の行、どのイベントで動くかは利用者の回答を待つ。それ以外の点だけ、既定の案を明示して進めてよい
5. **設定 JSON を保存** — 式の書き方（関数の引数、空のときの値、テーブルの中と外）に迷うときは、先に `fml_try`（try の章。同梱のサンプルアプリで実際のエンジンの結果）で確かめる。sample-settings の章の雛形を写し、**封筒**で `fml_save_settings` に渡す（path はアプリのフォルダーの中の `APP<番号>-<アプリ名>.json`。接続のファイルが無いときは `settings/APP<番号>-<アプリ名>.json` と `fields`）。`pluginID` は `"rex0220 formula plugin"`、`PluginVersion` は `fml_status` が出す zip の版。`pluginInfos` に計算式を置く項目の行（`fieldcode`、`state`、`formulaSet`、`edit`、`hide`、`rank`）だけ書く（他は normalize が補う）。**ランクは計算の順で、大きい順に計算する**（未設定は 0、同じならレイアウトの順）。**ランクは順が逆のときだけ付ける**（constraints の章の計算の順）。保存は normalize（検査）を通る。エラーがあれば invalid で保存されない（results の章の表で直して、もう一度 `fml_save_settings`）。**警告は消さずに利用者に伝える**
6. **calc** — `fml_calc`（path、records）。項目ごとの前後の値を見て、要件どおりか確かめる。評価は Worker で動き、60 秒で止まる（重い式なら `timeoutSec`）。文脈が足りない（APP_URL に接続先が無い、LOOKUP_GETID の項目がルックアップでない、ログインユーザーが決まらない）ときは名指しで止まるので、利用者に聞くか `user` を付ける。結果は模擬（レコードは更新しない）。ユーザー情報を使う式は既定のテストデータ（架空）の値、イベントで分岐する式は `event` の文脈（既定は「既存レコードを変更」と同じ `allUpdate`）で計算される。直すときは `fml_summary`（digest）→ `fml_update_fields` → もう一度 `fml_calc`
7. **反映方法を伝える（4 段）** — アプリの設定 → プラグイン → 計算式プラグインの設定 → **設定をアップロード** → 取り込み方を選ぶ（設定がまだ無いアプリは「全置換」、既存の設定に項目を足すなら「項目の置換」で対象の項目をチェック。**前の設定を取り込んだかは AI には分からないので決めつけない**: 分からなければ「まだなら全置換、取り込んであれば項目の置換で〇〇だけ」と両方を書く）→ **保存する**（「運用環境に反映」をチェックするとアプリの更新まで行う）→ 以後に追加・編集するレコードは新しい設定で計算 → **既存のレコードは変わらない**ので、**値を計算する項目の計算式・計算する／しない・ランクを変えたとき**（差分の ★）だけ、設定画面の「既存レコードを変更」か一覧の「一括計算」を利用者が実行するよう勧める。**ボタン・表示だけの変更**（ヘッダー `($HEADER1)`〜・スペース項目 `(要素ID)`・グループの行、編集・非表示）は押したとき・表示のときに動くので、既存レコードを変更をしても値は変わらない = 勧めない（「既存レコードの値は変わらないので、既存レコードを変更は要らない」と伝える）。本番のアプリへは、利用者が開発で確かめた同じファイルを本番の設定画面でアップロードする。**一覧 ID はアプリごとに違う**ので、一覧別設定は本番の設定画面で選び直すよう添える

副作用のある関数（FSET / FSET_TADD / BUTTON / DIALOG / CLIPBORD_WRITE）を使う式は、利用者にその旨を伝える（formula MCP は policy で承認したものだけ評価する。テンプレートの既定は BUTTON / DIALOG / FSET / FSET_TADD。AI は policy を書かない）。イベントで結果が変わる式（EV_INFO）を書くときは「どのイベントでどの値になるか」を表にして利用者に示す。
