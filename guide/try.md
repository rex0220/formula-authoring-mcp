# 式の試し計算（サンプルアプリ。`fml_try`）

利用者のアプリの項目定義とレコードが無くても、**同梱のサンプルアプリ（架空）で実際の計算式エンジンの結果を確かめられる**。

**使う場面（決まり）**: 関数の解説・使用例・式の断片は資料（function-list、patterns。✔ の例の結果は patterns-verified）で答える。`fml_try` を使うのは次の 3 つ: 利用者が動きの確認を求めたとき、資料に無い値や端の動き（空・範囲外・0 起点）を断言するとき、資料と自分の理解が食い違うとき。使うときは 10 式までまとめて 1 回（探索を続けない）。設定を作る流れ（保存 → `fml_calc` で実レコード）は変えない。

## サンプルアプリ

- スペース項目 `sp1`（要素 ID。式の返り値をそのまま返す）
- 全項目タイプ × 2（`文字列1` / `文字列2`、`数値1` / `数値2`、`日付1` / `日付2`、`日時1`、`時刻1`、`ドロップダウン1`、`ラジオ1`、`チェック1`、`複数選択1`、`ユーザー1`、`組織1`、`グループ1`、`リンク1`、`リッチ1`、`文字列複数行1` …）、グループ枠 `グループ枠1`（中に `枠内文字列1`、`枠内数値1`）、計算項目 `計算1` / `計算2`（kintone の計算。計算式は置けない）、システム項目（レコード番号、作成者、作成日時、更新者、更新日時）、カテゴリー、ステータス、作業者
- テーブル 2 つ `テーブル1` / `テーブル2`（テーブルに置ける型を各 1 つ。子は `T1_数値`、`T1_文字列`、`T1_日付`、`T1_ドロップダウン`、`T2_数値` … の接頭辞）
- ルックアップと関連レコード一覧は無い（`LOOKUP_GETID` / `RELATED_GETID` は試せない。利用者のアプリで `fml_calc`）
- レコード 3 件: **1** = 典型（全項目に値、テーブル1 3 行、テーブル2 2 行）、**2** = 端（0、負の小数、改行、未選択、月末と年末の日付、テーブル1 1 行、テーブル2 0 行）、**3** = 空（ほぼ全部空、テーブル 0 行）
- ユーザー・組織・グループの値は既定のテストデータ（架空の 10 人。`demo_user01` …。test-users の章）のコード。接続先は `https://example.cybozu.com`（`APP_URL` はこれで評価される）
- 正確な項目の一覧は `fml_try` に `describe: true`（1 項目 1 行。○ = 計算式を設定できる型）

## 使い方

- `fml_try`（formulas: `[{ formula, as?, table? }]`、1 回 10 式まで）。式ごとに 1 行だけの設定を組んで normalize（検査）→ calc（模擬）。式ごとに独立（1 つの誤りがほかを止めない）
- `as` は対象の型（`NUMBER` / `TEXT`（既定。文字列 1 行。どの値も文字列で見える）/ `DATE` / `DATETIME` / `TIME` / `DROP_DOWN` / `RADIO_BUTTON` / `CHECK_BOX` / `MULTI_SELECT` / `USER_SELECT` / `ORGANIZATION_SELECT` / `GROUP_SELECT` / `LINK` / `RICH_TEXT` / `MULTI_LINE_TEXT`）か項目コード。型のときは**式が参照していない項目**が対象になる（`数値1` を使う式なら `数値2`）。テーブルの中で計算する（行ごと）なら `table`（`テーブル1` / `テーブル2`）
- `records` で絞る（既定は 3 件とも）。文脈は `fml_calc` と同じ（`event`、`user`、`users`、`mobile`。ユーザー情報は既定のテストデータ）。副作用のある関数は policy で承認したものだけ評価する（テンプレートの既定は BUTTON / DIALOG / FSET / FSET_TADD。AI は policy を書かない）
- 結果の `results[].values[]`: `value` は対象の型に入れた後の値（kintone に保存される形。数値も文字列）。`raw` はエンジンの生の値（`value` と違うときだけ。数値は数、日付は epoch 秒、配列は配列）。`error` は評価の失敗。`findings` はその式の検査のエラー・警告（results の章の表）。`marks` は印（ユーザー情報、イベント、再計算で変わる、kintone の文脈）
- 対象を式が参照する（自己参照）と警告 `try.self-reference`: テーブルの外の項目は 1 段目と 2 段目の 2 回計算されるので値が 2 回分になる（実機と同じ）。`as` で式が使わない項目を選ぶ

## 架空の項目と値（利用者の項目コードや境界値で試す）

標本の項目と 3 件のレコードで足りないときは、入力で補える。値はすべて AI が作る架空のもの（**実在の個人情報・本番の値は入れない**）。

- **`fields`（標本に項目を足す）**: `[{ code, type, options?, table?, fields? }]`（10 個程度まで。上限 20、テーブルの子も数える）。`type` は TEXT / NUMBER / DATE / DATETIME / TIME / DROP_DOWN / RADIO_BUTTON / CHECK_BOX / MULTI_SELECT / USER_SELECT / ORGANIZATION_SELECT / GROUP_SELECT / LINK / RICH_TEXT / MULTI_LINE_TEXT / SUBTABLE。選択肢の型は `options` 必須（`["明細", "小計"]`）。`table` で既存のテーブルの子に、`type: "SUBTABLE"` + `fields` で新しいテーブル（子つき）。コードは標本の項目と重ねない。独立のアプリは作れない（標本に足すだけ）
  - 例: `[{ "code": "単価", "type": "NUMBER" }, { "code": "明細", "type": "SUBTABLE", "fields": [{ "code": "分類", "type": "DROP_DOWN", "options": ["明細", "小計"] }, { "code": "金額", "type": "NUMBER" }] }]`
- **`data`（架空の値のレコード）**: `[{ 項目コード: 値, … }]`（5 件まで）。土台は `base` の標本のレコード（既定 3 = 空。1 なら典型の値の上に書く）。書いた項目だけ変わる。`data` があるときは標本のレコードは `records` で選んだものだけ計算する
  - 値の書き方: 数値は数か数字の文字列（`100`、`"-12.5"`）、文字列はそのまま、日付 `"2026-03-31"`、時刻 `"09:30"`、日時 `"2026-03-31T00:30:00Z"`、ドロップダウン・ラジオは選択肢の値、チェック・複数選択は配列、ユーザー・組織・グループはコード（`"demo_user02"`。複数は配列。名前はテストデータから補う）、テーブルは行の配列 `[{ 子のコード: 値 }]`（20 行まで。書かない子は空）、空は `""`
  - 例: `[{ "単価": 100, "明細": [{ "分類": "明細", "金額": 200 }, { "分類": "小計", "金額": 200 }] }, { "単価": 0 }]`
  - 誤り（無い項目、選択肢に無い値、数でない）は `invalid` で名指し（`data[0].ドロップダウン1: 選択肢に無い値 "Z"（A / B / C）`）。テーブルの子はテーブルの行の中に書く
- **`app`（利用者のアプリの項目定義に架空の値）**: `app: <番号>`（接続のファイルがあればそのアプリのフォルダーの `fields.json`、無ければ `fields/<番号>.json`。`fml_fields` で取ったもの）。項目コードと選択肢が実機と同じになるので、要件の項目名のまま式を確かめられる。`data` が要る（標本のレコードは使えない）。`fields` で項目を足すこともできる（要件で足す予定の項目）。接続先（APP_URL）はその profile。ルックアップ・関連レコード一覧の文脈は `fml_calc` と同じ制限
- 結果の `app.source`（`sample` / `app`）、`app.records`（`"1"`〜`"3"` は標本、`"d1"`〜 は架空の値）、`app.extraFields`（足した項目）で、何で計算したかを利用者に伝える。`app` のときの `note` は「利用者のアプリの項目定義に架空の値を当てた模擬」

使い分け: 関数の動きだけなら標本で十分。利用者の項目名・選択肢で式を組んでから試すなら `fields` + `data`、項目定義を取ってあるなら `app` + `data`。実際のレコードで確かめるのは `fml_record` → `fml_calc`。

## ボタン（BUTTON / DIALOG）のクリック

ボタンの式（patterns の「ボタン・イベント」）は、式に `click: true` を付けると押した模擬も返す。`as` の省略はスペース項目 `sp1`（実機でボタンを置く場所）。テンプレートの policy は BUTTON / DIALOG / FSET / FSET_TADD を既定で承認している（外してあれば `formula.side-effect` で invalid → 利用者に頼む。AI は policy を書かない）。

- 手順は実機（デスクトップの buttonClick）と同じ: 押す前の表示（式の返り値）→ `EV_SET("click")` → 式（BUTTON / DIALOG が FSET / FSET_TADD を実行）→ 全項目の再計算 → 押す前のレコードとの差。レコードは写しで、kintone には何も送らない
- `values[].click.display` は押す前の表示（BUTTON: `TYPE` / `TITLE` / `CSS` / `DETAIL` / `EDIT`、DIALOG: `TITLE` / `HTML` / `ICON` / `SCAN`（キャンセルの有無）/ `CSS`）。`values[].click.changes` は押した後に変わる項目（`fieldcode` / `before` / `after`。計算式の無い項目も。テーブルは行の配列で、FSET_TADD で足された行が見える）。`errors` の `phases`: `display` = 返り値がボタンでない、`click` = クリック時の式の失敗（実機はエラーのダイアログを出してレコードを変えない）、`top` / `table` / `2nd` = 再計算の失敗
- 利用者の設定で確かめるなら `fml_calc` の `click`（ボタンの行の項目コード。スペース項目は `"(sp1)"` の形。計算後の実レコードで押す。`records[].click`）
- 答えるときは、押す前の表示と「押すと どの項目が 何になるか」をレコードごとの表にして示す。**最後は利用者が実機のテスト用アプリの編集画面で押して確かめる**（保存せずに閉じれば元に戻る。本番では押さない）。模擬しないもの: ボタンの見た目・位置・CSS・ダイアログの表示・`record.set` の後の change イベント
- 空の数値 + 1 は空のまま（constraints の空の扱い）なので、加算のボタンは `FSET(数値1, NVL(数値1, 0) + 1)`

## 答えるときに

- 「サンプルアプリでの模擬」であることと、値（空のときの値、端の値）を添える。利用者のアプリの項目・選択肢・レコードとは違う。利用者の設定を確かめるのは `fml_calc`
- 使用例を書くときは、資料の例（patterns の ✔、function-list の `ex:`）か `fml_try` で通った式を書く。通らなかった式（`formula.syntax`、`formula.unknown-function`）はそのまま答えに使わない
- 複数の書き方で迷うときは、まとめて 1 回の `fml_try`（10 式まで）で比べる
- スペース項目（HTML の表示。patterns の「スペース項目」）は標本の `sp1` を対象にできる（`as: "sp1"` か `"SPACER"`）。レコードに値が無いので、式の返り値（`ARRAY(ラベル, 書式, 値, 書式)` の配列や HTML）をそのまま返す。表示の確かめは実機で
- ボタン（BUTTON / DIALOG）の式は `click: true` で押した模擬も返す（下の「ボタンのクリック」）
- 利用者の項目名や選択肢で確かめたときは、それが架空の項目・値であること（`app` なら項目定義は実機、値は架空）を添える
